## The rule that governs this task

**The owner's URL list decides what goes in the sheet. SEMrush decides nothing.**

SEMrush audits the whole site. The fix sheet covers the money pages and posts
defined in `clients/registry.yaml` and nothing else. An issue SEMrush raises on
a privacy policy, a testimonial form or a jobs listing is not a client finding,
it is noise, and putting it in the sheet sends a VA to do work nobody asked for.

Every affected URL passes through `crawl_targets.scope_urls()` before it reaches
a cell. **If an issue has zero in-scope URLs, the whole row is dropped**, not
downgraded.

The first EW attempt ignored this and shipped five rows. Three of them were
wrong: Missing H1 pointed at `/resources/` and `/releases/`, the schema error
pointed at `/teacher-evaluation-software/`, and the duplicate-description row
claimed 30 pages. After filtering, two rows disappeared entirely and 30 became
**7**. The other 23 were the privacy policy, terms of service, about-us,
contact, the instructional-look-fors set and the individual case studies.

Every row's note states how many SEMrush flagged versus how many are in scope,
so the gap is visible rather than silently swallowed.

## Who fills what

| Field | Source |
|---|---|
| Site Health score, this month | `info` → `current_snapshot.quality.value` |
| Site Health score, last month | See below. Not free. |
| Site Health score, after fixes | 2.2, after the re-run |
| Fix sheet required? | Script: score <92% OR any issue with a positive `delta` |
| Issue Type | `meta_issues` → `title` |
| Affected URL(s) | `issue_details` → `source_url`, filtered to scope |
| Exact Change To Make | **Written, not fetched.** See below. |
| Proof / Link | Project audit URL |

### Last month's score is not free

`quality.delta` is the change against the **previous weekly crawl**, not against
last month. The month-ago figure needs the `history` report, which costs
**10,000 API units**, and on 2026-08-17 the balance could not cover it while
every 100-unit report worked fine. So it is a balance limit, not an access one.

Write `Not retrieved` with the reason, and record the current score. **From the
following month this cell fills from our own stored value**, the same pattern as
the indexation baseline in 1.2. Do not pay 10,000 units for a number that
becomes free by waiting one cycle.

### "Exact Change To Make" is written, never fetched

SEMrush's fix guidance is editorial content in its UI and is not exposed by the
API. `meta_issues` returns the issue title and column labels, nothing more.

This is the better outcome. SEMrush would say "fix duplicate meta descriptions".
The sheet has to say which pages, what they currently serve, and what to do.
**Verify live before writing the instruction**, because the audit snapshot is
days old and the API's verdict can already be wrong:

- EW's `/principal-for-the-day-ideas/` was flagged as a bad sitemap entry. Live
  it returns **410 Gone**, so the fix is to remove the sitemap entry, not to
  repair the page.
- Its duplicate descriptions are all one truncated site-wide default, and
  `/teacher-evaluation-software/` already has a proper unique one, proving the
  field works and is simply unpopulated. That detail changes the instruction
  from "write descriptions" to "the template default is filling in".
- SEMrush counted the schema error twice because it crawled the slash and
  non-slash URL. Both 200, both canonical to the slash version. **One page, one
  fix.** Deduplicate before writing a count.

Never instruct anyone to invent data. The `SoftwareApplication` schema missing
`aggregateRating` and `review` is fixed by supplying real reviews or removing
the block, never by making rating values up.

## What earns a row

Set by the owner on 2026-08-17 after SameDay shipped with a single row while it
had four errors and three structural notices, including a redirect loop.

| Severity | Rule |
|---|---|
| Error | **ALL of them, always.** No threshold, no exceptions. |
| Warning | 10% of sitemap URLs, or always for link integrity (broken links, broken images, missing H1, missing meta description) |
| Notice | 20% of sitemap URLs |

The denominator is the client's sitemap total, and the thresholds live in
`run_1_3.py` as `WARN_SHARE` and `NOTICE_SHARE` so they change in one place.

**Notices above 20% are not notices.** SameDay carries 178 permanent redirects
on a 305-URL sitemap, 146 orphaned sitemap pages and 87 pages more than three
clicks deep. SEMrush files all three as notices; at 58%, 48% and 29% of the site
they are structural defects, and two of them turned out to be single template
links. Anything at that scale gets a row.

Anything that lands just below a threshold is **named in the "Fix sheet
required?" note** rather than dropped in silence, so nobody wonders later
whether it was missed or judged.

Still excluded: "Low text to HTML ratio" on 307 WordPress pages. It clears the
share threshold and is still a theme artifact that names no fix.

## Errors get a second chance on path patterns

The scope set is built from the sitemap, which creates a circularity: a broken
page is frequently missing from the sitemap **precisely because it is broken**.

SameDay's redirect loop on `/emergency-services/air-conditioner-repair/` was
filtered out on exactly that basis, and it was the most severe finding on the
client, a revenue page that 301s to itself and can never be reached.

So for an **Error**, a URL sitting under one of the owner's money or post path
patterns counts as in scope even when the sitemap has forgotten it. Warnings and
notices still require sitemap membership.

## One URL per row

The Affected URL(s) column carries **one URL per row**, with the number and
issue type repeated down the group. Owner's requirement: the column has to be
selectable and pasteable straight into a browser, which a semicolon-joined list
in a single cell cannot do.

The instruction text sits on the first row of each group only. It is one
instruction, and repeating 900 characters down eight rows makes the sheet
unreadable without making it more useful.

### List EVERY affected URL, not a sample

`issue_details` defaults to 10 results. Pass a `limit` high enough to return the
whole set and write all of it. A truncated list is not a smaller version of the
finding, it is a different finding.

SameDay's orphaned-pages row was first written from the first 12 rows returned,
all of which happened to be blog posts, and the summary read "the entire blog".
Pulling all 146 showed **56 were service pages** - Lehi HVAC, Provo heating,
West Jordan electrical - money pages with no internal links at all. The sample
was not merely incomplete, it pointed at the wrong half of the problem and would
have sent the fix to the blog while the city pages stayed orphaned.

Where one SEMrush issue contains two populations needing different fixes, split
it into two rows. Orphaned service pages get linked from their parent city page
and the hub; orphaned posts need a blog index. One row would have merged two
different jobs.

### Count unique URLs, not rows

Link-level issues return one row per link instance, so counts can exceed the
size of the site: Superior reports 867 permanent redirects on a 344-URL sitemap.
Deduplicate before writing a count, and say both figures when they differ
("34 broken links, which are 5 dead destinations across 13 pages"). This is the
project's audit-workflow rule 10 and it applies here directly.

## Running it

```bash
python scripts/run_1_3.py <client> --data <fetched.json>
```

The SEMrush MCP tools are callable by the agent, not from Python, and there is
no SEMrush key in `.env`. So the agent fetches and the script filters and
writes. Fetch order per client, using the project id in the registry:

1. `info` with the project id → score, per-issue counts and deltas, snapshot_id
2. `issue_details` for each issue with `count > 0` that is an Error, plus any
   warning worth checking → affected URLs

`meta_issues` returns the same global catalogue for every project, so fetch it
**once** and reuse it. That saves 100 units per client.

**Arsenal is on a separate SEMrush account** (project `28428944`). It does not
appear in `list_projects`, which is what led to a wrong claim that it had no
project at all. Querying it directly by id works normally. Never conclude a
project is missing from `list_projects` alone.

## Gate

Done when the three score rows carry a value or a stated reason, `Fix sheet
required?` is answered, and every listed row names at least one in-scope URL
with an instruction specific enough for a developer to act on without asking a
question. A row whose URLs are all out of scope must not appear at all.
