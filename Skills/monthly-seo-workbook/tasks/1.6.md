# 1.6 Run AI Visibility Prompt Set & Log Share of Voice

> table, and no claim about a client may be written before the query is run.

**Tab:** `1.6 AI Visibility SOV` · **Owner:** Roger · **Blocked by 1.4**
**Runs — one command for the whole month:**

```bash
python scripts/monthly_1_6.py 2026-09          # all eight clients
python scripts/monthly_1_6.py 2026-09 beehive  # one client
```

The driver collects (skipping any platform whose file for the stamp is already
on disk, so a re-run after an interruption never re-pays for records) and then
fills sections A, B, C and the SOV header via `scripts/fill_1_6_all.py` — the
single engine for ALL EIGHT clients. It carries per-client brand regexes
(written against real collisions: "snow" is weather, "superior" is an
adjective, "sage advice" is not the ERP) and per-client competitor vendor maps
curated from the actual answers. `fill_1_6.py` / `fill_1_6_bc.py` were the
EW-only first build and are superseded; do not run them.

**Month-over-month is automatic.** The raw platform JSONs in
`Clients/<folder>/ai_visibility/` are the durable record; last month's SOV is
recomputed from them over the current prompt set and written into the header
with the delta. A move under **12 points prints as "no measurable change"** —
that is a hard reporting rule, not advisory. First month prints the baseline
note instead.

**Interrupted runs are free to recover.** Every trigger's snapshot id is
ledgered to `Clients/<folder>/ai_visibility/snapshots.log` the moment it fires;
Bright Data keeps completed snapshots server-side, so a dead session is
recovered by re-polling the id (see `monthly_1_6.py` docstring), never by
re-triggering. The 2026-08 crash cost one client's re-trigger only because the
ledger did not exist yet.

**On local home-services clients, ChatGPT answers with a MAP of business
listings, not prose.** Brand presence = answer text OR the record's
`business_locations`, and the Notes say when a mention is listings-only. This
is where the local competitors actually appear (Beehive shows up inside
SameDay's listings), and prose-only matching would report the local clients as
far less visible than they are.

## Provider: Bright Data, and what it does not cover

Auth is one bearer token in `.env` as `BRIGHTDATA_API_TOKEN`. Dataset ids are
hardcoded in `scripts/brightdata.py`, read from the account rather than guessed.

**Use the async trigger endpoint, never the sync one.** `/datasets/v3/scrape` is
zone-backed and returns `400 Customer is not active` on this account, which reads
as a suspended account and is not one. `/datasets/v3/trigger` needs no zone and
works. The trigger payload is a **bare list**, not `{"input": [...]}`.

Async is also the right shape regardless: one ChatGPT prompt took 110 seconds, and
a monthly run is 8 clients times ~33 prompts times 3 platforms.

**Do not create a Bright Data zone for this task.** Zones belong to the proxy
products. An afternoon went into configuring Web Unlocker before the async
trigger proved no zone was needed at all.

Coverage is split and neither provider is complete:

| Platform | Bright Data | DataForSEO |
|---|---|---|
| ChatGPT, Perplexity, Gemini | yes | yes |
| Google AI Mode, Copilot | yes | no |
| Claude | no | yes |

The tab has columns for **ChatGPT, AI Mode and Perplexity**. Gemini is worth
running anyway (it is consistently the strongest platform) but has no column, so
it goes in Notes and **never into the SOV figure**.

## Never force browsing

`web_search` is only sent to platforms that support it, and only when explicitly
asked for. ChatGPT is the sole platform that reports `web_search_triggered`, so
its browse state is recorded; the others decide internally and expose nothing,
and their rows must say the state is unknown rather than implying it was measured.

A browse-forced harness finds the brand in answers a real user session never
sees. That is the documented cause of the July 2026 over-reporting.

---

## Prompt sourcing: GSC and PAA only

**Every prompt traces to a real query.** No invented prompts, no prompts
generated by asking an AI what to track, no keyword export loaded unfiltered.
Prompts live in `clients/prompts/<client>.yaml` with the source query,
impressions and position on every row, and those three land in the sheet so any
row can be audited a year later.

Pull 16 months of GSC, filter to question-form and vendor-intent queries, sort by
impressions. Where a client has too little vendor-intent data, top up from
DataForSEO People Also Ask rather than inventing. **A thinner honest set beats a
full set that is half fabricated.**

Two traps that cost real time on the first build:

**Match on word boundaries.** `app` matched inside `appreciation` and filed EW's
entire teacher-appreciation corpus (parents writing thank-you cards) as
software-intent buyer demand.

**A name missing from the vendor map is invisible, not absent.** Observe4Success
was reported as appearing zero times in 99 responses and recommended for removal.
It appears 9 times. Nothing had ever searched for the string. Before claiming a
competitor is absent, confirm the map contains it.

## Sizing, and the noise floor

The published advice ranges from 10 prompts to 228 per topic, so most of it is
vendor convention. The only source that shows its working (Obsero) puts a single
prompt at roughly ±16pp of error: **one prompt is noise, a topic is a metric.**

At monthly cadence there is no cadence multiplier, so precision comes from prompt
count alone. **25 category prompts across 3 platforms is 75 observations, which
makes the month-over-month detection threshold about 12 percentage points.** At
10 prompts it is 20 points, which would report random variation as movement in a
tab that feeds the roadmap.

So: **25 category prompts in 4-5 topics, plus 5 branded and 3 competitor**, and
**never report a month-over-month delta below 12 points.** Month one is a
baseline and carries no deltas at all.

---

## SOV excludes branded prompts

Branded prompts return the brand nearly every time by construction. Folding them
in reports the brand recognising its own name as category visibility: on EW that
was the difference between a headline of 25% and the real figure of 9%.

Branded prompts still run, and are reported separately in the same cell.

---

## Report per platform, never blended

EW scored 4% on ChatGPT and 24% on Gemini. A single blended number would have
hidden a six-fold spread and misdirected every recommendation built on it.

---

## Reading the result: citation is not recommendation

The finding that mattered most on EW was not the SOV figure. `educationwalkthrough.com`
was the **most-cited domain of any source** across the category prompts, ahead of
every competitor, while the same assistants recommended other vendors when asked
which tool to buy.

That is a positioning problem on pages that are already being read, not a content
gap, and the two have opposite fixes. Section B exists to surface it: for each
money prompt it names who was recommended and which third-party page the model
read to get there, because getting listed on a page the model already cites is
faster than displacing its opinion.

## Sheet mechanics

- Section A anchors on the `#` header in **column A**. `find_rows` scans column A
  only, so anchoring on the section A label fails: it lives in column B.
- Rows 4-6 are **merged across A:C**, so the values go in **column D**. A write to
  B silently fails readback.
- Intent dropdown is `Discovery / Comparison / Best-X / Decision`. Best-X is
  superlative prompts, and it is distinct from Decision: being absent from a
  ranked list is a different failure from not being chosen once shortlisted.
- Section A ships with 26 rows and a full set is 33, so rows are inserted and the
  anchors re-read afterwards.

## Gate

Done when every prompt row carries its source query and impressions, the SOV cell
states the category figure with branded reported separately, section B names a
competitor and a third-party page for every money prompt, and no platform column
has been filled from a platform that was not actually queried.
