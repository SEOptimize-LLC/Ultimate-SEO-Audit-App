## Rules

### Sitemaps come in two shapes and they are not interchangeable

A `<sitemapindex>` lists child sitemaps to fetch. A `<urlset>` **is** the URL
list. Detect which before parsing.

Treating a flat urlset as an index makes every page look like an empty child
sitemap. That produced **101 false findings on Arsenal and 236 on Cudio**, both
written into live client workbooks before it was caught. Arsenal and Cudio use
flat sitemaps; Superior, SameDay, Beehive and Snow use indexes.

Also distinguish a child sitemap that is **genuinely empty** (0 URLs, minor)
from one that **failed to fetch** (unreachable, Fix This Month). They are
different problems and the earlier code reported both as "empty".

### A registered sitemap that 404s is a finding, not a crash

Comfort's `sitemap_index.xml` returns 404. Search Console is submitting a URL
Googlebot cannot fetch. Catch the fetch failure and log it as Fix This Month
rather than aborting the run.

### The Sitemaps API `indexed` field is deprecated. Never report it.

It returned **23 against 359 submitted** on Superior. Write "Indexed count NOT
available" in the cell and say why. The honest source is `index_audit.py`.

### TTFB is not a Core Web Vital

LCP, INP and CLS are. Report a POOR reading on any of those as Fix This Month.
Report TTFB as **Watch**, never as a CWV failure: it sends someone optimising
the wrong layer. On Superior every Core Web Vital passes and only TTFB
(853-925ms) is off GOOD, so "real failures only" correctly reads as none.

### Severity is assigned by rule, not by judgement

| Condition | Severity |
|---|---|
| noindex on any crawled page | Blocker |
| non-200 on a **top-5** money page | Blocker |
| non-200 elsewhere | Fix This Month |
| redirect chain of 2+ hops | Fix This Month |
| canonical pointing to a different URL | Fix This Month |
| Core Web Vital POOR in field data | Fix This Month |
| sitemap unreachable / GSC sitemap errors | Fix This Month |
| empty child sitemap, GSC warnings, TTFB | Watch |

Top 5 means the first five rows of 1.1 section C, so 1.1 must run first even
though 1.2 is not formally blocked by it.

### A clean sweep still writes a row

"No issues found this sweep" goes in the findings log. A blank tab is
indistinguishable from a task nobody ran, which is the workbook's own rule.

## Which URLs get crawled

**The owner defines the money pages. Never infer them.** Every client's set was
supplied directly on 2026-08-17, and every one was narrower than what pattern
matching had been guessing: Cudio was crawling `/industries/` as well as
`/services/`, Beehive was pulling 27 PPC and utility pages into the money set,
and Arsenal was matching four subfolders instead of its 39 named pages. Those
inflated the money-page count in check 5 on every earlier run.

Three mechanisms, all in `clients/registry.yaml` under `crawl:`, chosen by
whichever describes that client most simply:

| Mechanism | Key | Use when | Example |
|---|---|---|---|
| Allowlist | `money_pages` | The set is a specific list | Arsenal, EW |
| Subfolder patterns | `money` | The set is whole sections | Superior, SameDay, Cudio, Snow |
| Sitemap minus exclusions | `money` + `money_exclude` | Easier to name the rejects | Beehive |

`money_pages` wins outright when present. `money_exclude` matches exact URLs
with trailing slashes normalised, so a list can be pasted straight from a
sitemap. The homepage is added automatically on every client and never needs
listing. `exclude` is separate and drops whole language sections, which is how
EW's `/es/` and `/ar/` stay out.

Posts come from `posts` patterns, matched against child sitemap filenames or
URL paths, so `post-sitemap` picks up `post-sitemap1/2/3` in one entry. The 15
newest are taken by real publish date from the WordPress REST API, falling back
to sitemap `lastmod` only on non-WordPress clients, where the note says so.

**When a spec names one sitemap or one subfolder, follow it literally and say
what that excluded.** Beehive's spec named only `page-sitemap`, leaving out
`plumbing-location-sitemap`; Cudio's named only `/services/`, dropping
`/industries/`. Both are recorded as comments in the registry next to the
setting, so the decision is visible to whoever reads it next rather than
looking like an oversight.

## check 3 via index_audit.py

`python scripts/index_audit.py <client>` inspects every sitemap URL through the
URL Inspection API and returns Google's own verdict per URL: *Submitted and
indexed*, *Crawled - currently not indexed*, *Discovered - currently not
indexed*, *URL is unknown to Google*.

Those states are not interchangeable. Crawled-not-indexed, and a page that
dropped out of the index, pass a **render check first** (added 2026-11-10,
`run_index_checks.render_gate`): a page whose same-site stylesheets or scripts
robots.txt blocks for Googlebot, or whose raw HTML carries under 50 words, routes
to 2.1 as a rendering fix. Only pages that render clean route to 1.8 as a quality
reading, confirmed with Test live URL (the API cannot run a live test). A page the
check could not fetch reads "render not checked", never clean.
Discovered-not-indexed points to discovery and internal linking; crawl budget
only matters at the scale Google's guide names (1M+ pages changing weekly, or
10,000+ changing daily). *Duplicate without user-selected canonical* means Google picked the
canonical for us, which is a different fix again. They must never be summed
into one "not indexed" number.

**Build one client per thread.** `googleapiclient` wraps each service in a
single `httplib2.Http`, and that object is not thread-safe. Sharing one across
a pool interleaves writes on the same socket: at 4 workers it lost 9 of 12
URLs, and at 8 it hung outright for fifteen minutes on a 101-URL site. With a
`threading.local()` client per thread, 8 workers is stable. This was originally
misdiagnosed as network flakiness and "fixed" by going serial, which hid the
real cause and cost roughly four times the runtime.

Budget ~1.1 s per URL at 8 workers: about 2 minutes for 100 URLs, 20 for 1,000.
A single call costs ~7 s of latency no matter what, so throughput comes from
concurrency, not from waiting. Quota is 2,000 URLs/day and 600/minute per
property, and neither binds at this rate.

`run_index_checks.py` writes checks 3 and 4, and completes check 6 by supplying
the indexed count the Sitemaps API cannot. It is a separate entry point from
`run_1_2.py` because it is separately triggerable and far slower. Re-running it
replaces only its own findings, identified by their `<n> URL(s)` opening; 1.2's
rows are left alone.

### The API has no history. We are the history.

URL Inspection returns current state and nothing else. There is no parameter,
no endpoint and no workaround for asking what a URL's state was last month.

So results cache to
`Clients/<name>/Monthly SEO Workbook/<YYYY-MM>/index_audit.json` and the next
month diffs against them. **That diff is the point**: a URL indexed in August
and crawled-not-indexed in September is precisely what check 3 asks for, and
the GSC UI will not tell you which URLs changed, only that a count moved.

The consequence is that a client's first run can only ever say BASELINE, and
the sheet says exactly that rather than implying a comparison happened. Never
delete a month's `index_audit.json`: deleting it does not lose a report, it
loses the only copy of that month's state.

The same no-history rule covers `watchlist.json`, which
`scripts/index_watchlist.py` writes into the same month folders. That script
answers the narrower operator question "are THESE pages getting indexed?" for
a named URL set (a `watchlist:` list on the client in `clients/registry.yaml`,
or `--urls-file`) - pages under remediation or a batch published this month.
It snapshots their current URL Inspection states and prints each URL's
month-over-month progression, pulling history from both files, so a watched
URL that was already covered by the sitemap-scoped audit shows its earlier
states too. Never delete a month's `watchlist.json` either.

## check 4 via the same run

Crawl Stats has **no API of any kind**. It is a Search Console UI report, and
nothing in the v1 surface exposes Googlebot request volume, the response-code
mix over time, host status or file types. Do not go looking again.

What the same inspection pass does yield, per URL, is `lastCrawlTime` and
`pageFetchState`. Aggregated, those give two things that answer the question
check 4 is actually asking:

- **Crawl recency** bucketed 0-7d / 8-30d / 31-90d / 90d+ / never, plus the
  median age. Month over month, a swelling 90d+ bucket means coverage is going
  stale, which is the same conclusion a Crawl Stats decline would support.
- **Fetch failures**, which unlike Crawl Stats name the specific URLs.

This counts URLs, not requests. Crawl Stats counts Googlebot hits including
repeat crawls of the same URL, so the two numbers are not comparable and the
note in the sheet leads with "CRAWL RECENCY PROXY, not Crawl Stats" so nobody
quotes it to a client as the real report.

**`PAGE_FETCH_STATE_UNSPECIFIED` is not a failure.** It is what a URL Google has
never discovered returns. Counting it as one invents a server problem out of a
discovery problem *and* double-counts the very same URLs already reported as
unknown to Google, which is what the first Arsenal run did before this was
excluded.

## Verify before you report (added 2026-10-05)

`run_1_2.py` and `run_index_checks.py` write the tab; neither grades its own work.

    python scripts/verify_1_2.py <client|all>            # checks 2, 5, 6, 7 and the severities
    python scripts/verify_1_2.py <client|all> --index    # checks 3, 4 and the indexed count

The first re-derives each check with different code: Google's status feed, the
sitemap re-fetched and re-counted, every crawled URL re-fetched with a real HTML
parser (noindex from the `X-Robots-Tag` header AND meta robots/googlebot in either
attribute order, canonical in either attribute order), PageSpeed re-queried. The
second recounts every figure from the per-URL cache, rebuilds the month-over-month
diff from last month's cache, and re-inspects 40 random URLs through a separate
client. "ALL MATCH" is required before 1.2 is called done.

**A check that is blank is a finding, not a pass.** The writer withholds a
degraded result (for example CWV that is only available site-wide) and leaves the
cell empty; the verifier lists it as needing a human look.

**Open (2026-10-05): "URL is unknown to Google" and "Discovered - currently not
indexed" are not stable states.** Re-inspecting the same URL within an hour flips
it between the two, in both directions, on every client (about 1 in 8 sampled
URLs); indexed, crawled-not-indexed and noindex never flipped. The split moves
the month-over-month figures far more than the union does (SameDay: discovered
52 to 24 while unknown went 9 to 31, union 61 to 55). Until the owner decides how
to report it, read the two as one "not yet crawled by Google" bucket.

## Calibration

**2026-08-14 — first run, all eight clients.**

- *Sitemap shape must be detected, not assumed.* 337 false findings shipped to
  two live workbooks before this was caught. Ruled out: inferring shape from the
  filename, since Arsenal's flat sitemap is called `sitemap.xml` and so are
  several indexes.
- *Read-back verification proves the write, not the data.* Every one of those
  337 false rows verified clean on read-back. Verification confirms a cell holds
  what was sent; it says nothing about whether what was sent is true.
- *Sheets API allows 60 reads and 60 writes per minute per user.* A batch across
  eight workbooks exceeds it. `sheets_io._call` now backs off on 429; without it
  a run half-completes, which is worse than being slow.
- *ADC expired after 3 days* (2026-08-14 to 2026-08-17), and re-authenticating
  with added scopes silently dropped the quota project. Suspected cause: consent
  screen set to External + Testing. Set it to Internal.

**2026-08-17 — checks 3, 4 and 6 automated, first index audit across all eight.**

- *The shape bug had a second home.* `index_audit.py` carried its own copy of
  the assume-it-is-an-index logic and silently returned **0 URLs** on Arsenal.
  Fixing a defect in one file is not fixing it: grep for the pattern, not the
  file. It now delegates to the single `sitemap_counts` that already knew better.
- *`httplib2.Http` is not thread-safe, and the symptom looks like bad network.*
  Shared across a pool it drops requests at low concurrency and hangs at higher
  concurrency. The first diagnosis was "flaky SSL" and the first fix was to go
  serial, which worked, hid the cause, and cost 4x the runtime. When concurrency
  "works but loses some", suspect a shared client before suspecting the network.
- *A state that means "not yet" must never be reported as a state that means
  "failed".* `PAGE_FETCH_STATE_UNSPECIFIED` was written up as "Google could not
  fetch", inventing a server problem and double-counting URLs already reported
  as unknown to Google. This is the fourth time a tooling artifact nearly
  shipped as a client finding. Before writing any finding, ask what the field
  means when nothing is wrong.
- *Appending to a findings log duplicates it on re-run.* Not clearing was a
  deliberate choice to protect 1.2's rows, and it produced a sheet showing both
  a wrong finding and its correction. Own your rows explicitly and replace them.
- *URL Inspection reports the PAST. Never state a live fact from it.* This is
  the most expensive lesson in this file. SameDay showed 98 URLs "Excluded by
  noindex", and the finding shipped as "98 URLs in the sitemap carry a noindex
  tag". They do not. All 98 were last crawled 2026-06-30, the day after the
  relaunch, and a 12-URL live sample found the tag on **none**: every one
  returns 200 with `follow, index` and 1,400 to 2,200 words. The tag was
  removed weeks ago and Google has not re-crawled to notice.

  The two situations read identically in the API and need opposite fixes. "The
  tag is present" means remove it. "Google's record is stale" means the work is
  already done and the pages need re-crawling. Sending a developer to strip
  noindex from 98 pages that do not have it wastes their week and leaves the
  real problem untouched.

  `live_noindex()` now samples up to 12 of them, and the finding is worded from
  what the sample actually found. When the tag is gone it is a **Blocker**, not
  a hygiene item: those are indexable revenue pages sitting out of the index for
  no current reason. The same caution applies to every other coverage state,
  because all of them are last-crawl verdicts. Check `lastCrawl` before treating
  any of them as current.
- *Handle every state, or add a catch-all that reports the ones you did not.*
  Two clients returned "Duplicate, Google chose different canonical than user"
  and nothing reported it, because the code only knew the similarly-named
  "Duplicate without user-selected canonical". Those mean opposite things: one
  is a missing canonical, the other is a canonical Google overruled. A generic
  "state we have no rule for" finding now catches anything unhandled, and it
  immediately earned its place by surfacing **98 SameDay URLs excluded by
  noindex**, 32% of that sitemap, which check 5 could never see because it
  crawls only money pages and recent posts. Match noindex on substring: Google
  returns the state with curly quotes and an equality check misses it.
- *The double-count has two directions.* After excluding the fetch state that
  means "not yet", Beehive shipped a single URL twice from the other side: once
  as coverage state `Redirect error`, once as fetch state `REDIRECT_ERROR`. A
  fetch failure is only worth its own row when the coverage state does not
  already explain it, so fetch findings are now filtered to URLs whose coverage
  state is otherwise benign.
- *Zero URLs is not a measurement of zero.* Comfort's sitemap 404s, so the
  inspection set was empty and the run wrote **Pass** on both checks, printed
  "Median age Noned", and told check 6 that 0 of 0 URLs were indexed. Worse, a
  later pass wrote "Indexed: 10 of 10 sitemap URLs (100%)" from the fallback
  sample, which reads as a perfectly indexed site. It now falls back to 1.1's
  top landing pages, labels the scope SAMPLE ONLY in the note, raises a
  Fix This Month finding saying the rest of the site is unmeasured, and leaves
  check 6 alone because a sample cannot answer "sitemap count vs indexed count".
- *A fallback must persist and remember itself.* The sampled result was first
  computed in memory only, so the cache still held the empty file and next
  month would have diffed against nothing. Persisting it then created the
  opposite bug: the next run saw 10 real rows, forgot they were a sample, and
  reported them as the whole site. The flag is written into the cache and read
  back out of it.
- *Every finding title must match the ownership pattern or it duplicates.*
  Adding the sample-fallback row without adding it to `MINE` meant re-runs
  appended it instead of replacing it. When adding a finding, add its title to
  that pattern in the same edit.
- *A cache from an older version of the script is not a cache.* Superior's
  August file was written by a test run before the `crawl` key existed, and
  reading it took the whole client down with a `KeyError`. Any cache is now
  checked for the keys the current code depends on and re-fetched if it is
  missing one. A partial test run left in the cache directory is the same trap:
  that file held 60 of 358 URLs and would have been reported as the full site.
- *Google's own answer is not perfectly stable.* Two Arsenal runs minutes apart
  returned identical indexed counts (94 both times) but shuffled the small
  non-indexed tail (unknown 3 to 1, discovered-not-indexed 0 to 2). Treat the
  indexed count as solid and single-URL movements within the non-indexed states
  as noise. A "dropped out of the index" finding requires the previous state to
  be *Submitted and indexed*, which is the stable end of the scale, so the
  Blocker rule is not exposed to this flapping. Do not lower that bar.

**Findings from the first run worth carrying forward:** Arsenal returns HTTP 410
on a top-5 money page, SameDay and Beehive each have a 301 on one, three 6-hop
redirect chains sit across SameDay and Beehive, and Comfort's registered sitemap
404s. Expect the redirect chains to trace back to their permalink restructures.
